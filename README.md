# Remnawave Limiter

**Централизованный контроль устройств для Remnawave**

Мониторит одновременные подключения пользователей через API панели: собирает IP со всех нод, сравнивает с лимитом устройств каждого пользователя (`hwidDeviceLimit`) и реагирует на превышения — через Telegram-бота или автоматической блокировкой подписки.

## Возможности

- **Агрегация IP со всех нод** — полная картина подключений, сравнение с индивидуальным лимитом + погрешность (tolerance)
- **Два режима:** `manual` — алерт с inline-кнопками (сброс, бан, whitelist); `auto` — автоблокировка с автовосстановлением по таймеру
- **Порог нарушений** — действие только после N превышений за окно (защита от ложных срабатываний)
- **Группировка** IP по подсетям (`/24`) или по ASN-провайдерам — против CGNAT и шаринга
- **Webhook** (JSON POST) о нарушениях с HMAC-подписью
- **Статистика и отчёты** — команда `/stats` (за 24ч/неделю + топ-5 нарушителей) и ежедневный отчёт в чат
- **Проверка обновлений** — раз в сутки сверяет версию с последним релизом на GitHub и сообщает в чат о новой
- **Мониторинг трафика** — сравнивает суточный трафик пользователя с его собственной нормой: всплески и постоянно высокий трафик, без запросов на каждого пользователя
- **Рантайм-настройки** через `/settings` — изменение параметров на лету без перезапуска (хранятся в Redis)
- **Whitelist** пользователей и IP/CIDR, кулдаун, кэш, выбор часового пояса, ru/en/zh
- **Liveness `/healthz`** (опционально, по `HEALTH_ADDR`) для healthcheck в Docker/оркестраторе
- **Логи под `docker compose logs -f`** — сводка по каждому циклу проверки, уровень меняется на лету, `LOG_FORMAT=json` для Loki/ELK

## Архитектура

```
┌─────────────┐     ┌──────────────────┐     ┌───────────────┐
│  Remnawave  │◄────│  remnawave-      │────►│   Telegram    │
│  Panel API  │     │  limiter         │     │   Bot API     │
└─────────────┘     │  (Go binary)     │     └───────────────┘
                    │  ┌────────────┐  │
                    │  │   Redis    │  │
                    │  └────────────┘  │
                    └──────────────────┘
```

Один инстанс рядом с панелью или на любом сервере. Установка на ноды не нужна — всё через API. Docker Compose поднимает сервис + Redis.

**Цикл проверки:** список нод (`GET /api/nodes`) → параллельный сбор IP по нодам → агрегация по пользователю → фильтр по `lastSeen` → сравнение с `лимит + погрешность` → инкремент порогового счётчика → при достижении порога реакция (алерт или автоблокировка).

Сбойная нода не роняет цикл: проверка выполняется по остальным, а в лог идёт предупреждение о неполных данных. Если не ответила ни одна нода, цикл пропускается целиком — иначе отсутствие подключений было бы прочитано как «все в пределах лимита».

## Требования

- Docker и Docker Compose
- **Remnawave 3.0.0+** с API-токеном (scope `connections:*`, `users:*` и `nodes:read`; для блока HWID в алертах ещё `hwid-user-devices:read`, для мониторинга трафика — `bandwidth-stats:node-usage`)
- Telegram-бот ([@BotFather](https://t.me/BotFather))

### Какую версию limiter выбрать

| Версия панели Remnawave | Версия limiter |
|---|---|
| **3.0.0 и новее** | **4.0.0+** — текущая, тег `latest` |
| ниже 3.0.0 (ветка 2.x) | [3.0.0](https://github.com/syvlech/remnawave-limiter/releases/tag/3.0.0) — последняя с поддержкой панелей 2.x |

Версии совместимы только в одну сторону: в Remnawave 3.0.0 модуль `ip-control` переименован в `connections`, а пользователи идентифицируются числовым `id` вместо `uuid` — старые эндпоинты удалены. Поэтому limiter 4.0.0+ не работает с панелью 2.x, а limiter 3.0.0 — с панелью 3.x.

Если панель ещё не обновлена, зафиксируйте образ на релизе 3.0.0 в `docker-compose.yml`:

```yaml
image: ghcr.io/syvlech/remnawave-limiter:b422f43
```

`b422f43` — коммит релиза 3.0.0. Отдельного тега образа `3.0.0` в ghcr нет: CI собирает semver-теги только для рефов вида `v*`, а релиз помечен как `3.0.0` без префикса.

## Установка

```bash
mkdir -p /opt/remnawave-limiter && cd /opt/remnawave-limiter

curl -O https://raw.githubusercontent.com/syvlech/remnawave-limiter/master/docker-compose.yml
curl -O https://raw.githubusercontent.com/syvlech/remnawave-limiter/master/.env.example

cp .env.example .env && nano .env
```

Обязательные параметры в `.env`:

```bash
REMNAWAVE_API_URL=https://panel.example.com
REMNAWAVE_API_TOKEN=your-api-token-here
TELEGRAM_BOT_TOKEN=123456:ABC-DEF1234ghIkl-zyx57W2v1u123ew11X
TELEGRAM_CHAT_ID=-1001234567890
TELEGRAM_ADMIN_IDS=123456789
LANGUAGE=ru
```

Запуск, логи и обновление:

```bash
docker compose pull && docker compose up -d   # запуск / обновление
docker compose logs -f limiter                # проверка
```

Все настройки — через `.env` или переменные окружения.

Для панелей за прокси/Cloudflare/защитой |

| `WEBHOOK_URL` | — | URL для webhook при нарушениях (POST JSON). Пусто = выключен |
| `WEBHOOK_SECRET` | — | Секрет webhook для HMAC-SHA256 подписей `X-Signature` (тело) и `X-Signature-V2` (`<X-Timestamp>.<тело>`). См. [Webhook](#webhook) (опционально) |
| `WEBHOOK_SECRET_HEADER` | `true` | Передавать ли сам секрет в заголовке `X-Webhook-Secret`. Оставлено ради совместимости; если получатель проверяет подпись — выключите |
| `WHITELIST_USER_IDS` | — | Числовые ID пользователей для исключения из проверки (через запятую). UUID из версий до 4.0 здесь не работают |

| `IGNORE_DURATION` | `0` | Время действия кнопки «Игнорировать» (мин). `0` = навсегда. `> 0` = временный whitelist с TTL |
| `VIOLATION_THRESHOLD` | `3` | Сколько нарушений нужно для действия. 1 = мгновенная реакция |
| `VIOLATION_THRESHOLD_WINDOW` | `3600` | Окно подсчёта нарушений (сек). Должно быть больше `(VIOLATION_THRESHOLD − 1) × (COOLDOWN + CHECK_INTERVAL)`, иначе порог недостижим и конфиг не принимается |

На логику ограничения не влияет — решения только по количеству IP/подсетей/ASN.

## Логика лимитов

| `hwidDeviceLimit` | Поведение |
|:-:|----------|
| `> 0` | Используется как лимит устройств |
| `null` | Берётся `DEFAULT_DEVICE_LIMIT` из конфига |
| `0` | Без ограничений — пользователь пропускается |

## Порог нарушений

При `VIOLATION_THRESHOLD=1` реакция на каждое превышение. При большем значении (по умолчанию 3) действие выполняется только после накопления N нарушений в окне `VIOLATION_THRESHOLD_WINDOW`: превышение → проверка cooldown → инкремент счётчика (TTL = окно) → при достижении порога действие и сброс счётчика. Если между нарушениями проходит больше окна — счётчик обнуляется.

Cooldown ставится до инкремента, поэтому счётчик растёт не чаще раза за `COOLDOWN`, а следующее нарушение замечается на ближайшей проверке. Окно должно вмещать `N − 1` таких шагов: `VIOLATION_THRESHOLD_WINDOW > (VIOLATION_THRESHOLD − 1) × (COOLDOWN + CHECK_INTERVAL)`. Конфиг, где это не выполняется, отклоняется при старте и в `/settings` — иначе порог никогда не был бы достигнут и лимитер молча перестал бы действовать.

Пример при `VIOLATION_THRESHOLD=3`, `VIOLATION_THRESHOLD_WINDOW=3600`:

| Время | Счётчик | Действие |
|:---:|:---:|----------|
| 12:00 | 1/3 | Лог, без действия |
| 12:05 | 2/3 | Лог, без действия |
| 12:10 | 3/3 | Алерт/блокировка, сброс |
| 12:15 | 1/3 | Лог, без действия |

## Telegram-бот

Все сообщения бота — **rich-сообщения** Telegram (Bot API 10.3, `sendRichMessage`): заголовки, таблицы, сворачиваемые блоки, время в часовом поясе читателя (`tg-time`) и цветные кнопки прямо внутри сообщения. Если Telegram отклонит rich-разметку, сообщение всё равно уйдёт — обычным текстом с inline-кнопками. Для отображения нужен клиент Telegram с поддержкой rich-сообщений.

### Команды

Доступны только администраторам из `TELEGRAM_ADMIN_IDS`. Регистрируются в меню бота автоматически при старте.

| Команда | Что делает |
|---------|------------|
| `/settings` | Интерактивное меню рантайм-настроек. Меняет безопасные параметры на лету (без перезапуска); значения сохраняются в Redis и переживают рестарт. Подробнее — раздел «Рантайм-настройки» ниже |
| `/stats` | Статистика нарушений: количество за последние 24 часа и за неделю + топ-5 нарушителей за неделю. Кнопка «🔄 Обновить» перерисовывает отчёт на месте |

### Рантайм-настройки (`/settings`)

Приоритет источников: **Redis-override > `.env` / переменные окружения > значения по умолчанию**. Изменения применяются на лету (например, `CHECK_INTERVAL` пересоздаёт тикер). Структурные и секретные ключи (API URL/токен, все `TELEGRAM_*`, `REDIS_URL`, `TIMEZONE`, `LANGUAGE`, `WEBHOOK_*`, `IP_WHITELIST`, `IGNORED_NODE_UUIDS`, `MAXMIND_*`, `DAILY_REPORT_TIME`, `HEALTH_ADDR`, `LOG_FORMAT`, `REMNAWAVE_COOKIES`, `REMNAWAVE_HEADERS`, `WHITELIST_USER_IDS`, `ASN_DATABASE_PATH`, `TRAFFIC_IGNORED_NODE_UUIDS`) меняются **только** через `.env` + перезапуск. Кнопка «Сбросить к .env» (для ключа или для всех, с подтверждением) убирает override.

Меню работает в одном сообщении, которое перерисовывается на месте:

- **Главный экран** — таблица всех параметров по разделам (🎯 Обнаружение, 🛡 Действия, ⏳ Пороги и кулдауны, 🌐 Группировка, 📈 Трафик, 🧰 Сервис); ♻️ отмечает значения, изменённые в боте.
- **Раздел** — значения, подсказки к каждому параметру и кнопки: флаги переключаются одним нажатием (включённые — зелёные), остальные открывают экран редактирования.
- **Редактирование** — текущее значение, источник (`.env` или бот), имя переменной, быстрые пресеты (для минут — в человекочитаемом виде, `0` = «навсегда») и ввод своего значения сообщением. Ошибка валидации показывается на том же экране, ввод можно сразу повторить.

### Ежедневный отчёт (`DAILY_REPORT=true`)

Раз в сутки в `DAILY_REPORT_TIME` (локальное время в `TIMEZONE`) бот присылает в чат тот же отчёт, что и `/stats` (нарушений за 24ч/неделю + топ-5). Учитываются только реальные срабатывания после порога `VIOLATION_THRESHOLD`; «мягкие» предупреждения в статистику не попадают. `DAILY_REPORT` переключается на лету через `/settings`, время `DAILY_REPORT_TIME` — только перезапуском.

Если включён мониторинг трафика (`TRAFFIC_MONITOR=true`), в отчёте есть раздел «📈 Постоянно высокий трафик». В нём пользователи, у которых за последние 7 закрытых суток набралось не меньше `TRAFFIC_HEAVY_DAYS` суток от `TRAFFIC_HEAVY_GB`, по убыванию трафика за неделю: сколько таких суток и сколько всего за 7 дней. Показывается до 10 пользователей, белый список пропускается. Отдельный алерт по такому пользователю приходит не чаще раза в 7 дней, а в отчёте он виден каждый день.

### Проверка обновлений (`UPDATE_CHECK=true`)

Через минуту после старта и дальше раз в сутки лимитер запрашивает последний релиз репозитория на GitHub (`api.github.com`, без токена). Если он новее запущенной версии, бот присылает в чат текущую и новую версию, команду обновления и кнопку «📝 Что нового» со ссылкой на релиз. О каждой версии сообщается один раз: последняя объявленная версия хранится в Redis (`update:notified`), поэтому перезапуски не дублируют уведомление. Черновики и pre-release не учитываются. Ошибки сети и лимит запросов GitHub только пишутся в лог (`warn`). Запрос идёт напрямую или через `HTTPS_PROXY`, если он задан. Выключить можно через `UPDATE_CHECK=false` или в `/settings` → «🧰 Сервис».

### Мониторинг трафика (`TRAFFIC_MONITOR=true`)

Лимитер сравнивает суточный трафик каждого пользователя с его собственной нормой и сообщает о двух ситуациях:

- **Всплеск.** За сутки пользователь потратил в `TRAFFIC_SPIKE_FACTOR` раз больше нормы и не меньше `TRAFFIC_SPIKE_MIN_GB`. Норма — медиана трафика за те из 14 предыдущих суток, когда пользователь пользовался подпиской: один необычный день её почти не сдвигает. Сутки без трафика — это отсутствие данных, а не нулевой трафик. Поэтому, пока таких суток меньше 5 (новая подписка, возвращение после перерыва), всплески по пользователю не считаются. Так видны взлом аккаунта, начало раздачи или перепродажи.
- **Постоянно высокий трафик.** Не меньше `TRAFFIC_HEAVY_DAYS` суток из последних 7 с трафиком от `TRAFFIC_HEAVY_GB`, причём последние сутки тоже тяжёлые. Так видны сидбоксы и перепродажа: у них высока сама норма, и всплеска нет.

Алерт приходит в тот же чат с теми же кнопками, что и алерт о лимите устройств. В нём трафик за сутки, норма и во сколько раз она превышена, три ноды с наибольшим трафиком, нарушения лимита устройств за неделю и диаграмма за 14 суток. Мониторинг только уведомляет и сам никого не отключает. Пользователи из белого списка пропускаются. Повторный алерт о всплеске по тому же пользователю приходит не раньше чем через 3 суток, о постоянном трафике — через 7. В ежедневном отчёте (`DAILY_REPORT=true`) такие пользователи видны каждый день, в разделе «📈 Постоянно высокий трафик».

**Пример.** Норма `ivan` — 6 ГБ в день (медиана за 14 суток). Раз в 30 минут лимитер одним запросом получает трафик за сегодня по всем нодам и складывает его по пользователю:

- в 09:00 у `ivan` 60 ГБ (DE-1 40 + NL-1 20): это ×10, но меньше 150 ГБ, алерта нет;
- в 11:30 у `ivan` 180 ГБ: больше max(10 × 6, 150) = 150 ГБ, приходит «📈 Необычный трафик» с превышением ×30.

У `petr` норма 15 ГБ, сегодня он скачал 130 ГБ. Это ×8.7, меньше ×10, алерта нет: для тяжёлого пользователя это разовая крупная загрузка. У `seedbox` последние 7 суток — 240, 190, 280, 260, 220, 300, 250 ГБ. Норма у него сама около 250 ГБ, поэтому всплеска нет. Но 6 суток из 7 больше 200 ГБ, и после смены суток приходит «📈 Постоянно высокий трафик».

**Сутки и история.** Сутки панель считает по UTC, по Москве они сменяются в 03:00. После смены лимитер один раз запрашивает прошедшие сутки целиком, записывает итоги в свою историю в Redis (16 суток, все пользователи с трафиком от 100 МБ на ноду) и проверяет их обоими правилами. При первом включении он сразу загружает из панели последние 14 суток (14 запросов), поэтому всплески считаются с первого опроса. Если панель старую историю не хранит, всплески начнут считаться после 5 суток работы.

**Ноды.** Запрос идёт по всем нодам панели, кроме `IGNORED_NODE_UUIDS` и `TRAFFIC_IGNORED_NODE_UUIDS` (например, нод, где большой трафик — норма). Отключённые ноды тоже учитываются: трафик за сегодня у них мог быть. Число нод на стоимость не влияет: панель хранит строки только там, где пользователь реально был. Если ему доступны 20 нод из 100, у него не больше 20 строк за сутки.

Порог панель применяет к паре «нода + пользователь», а не к сумме по всем нодам. Поэтому днём лимитер спрашивает с порогом в десятую часть `TRAFFIC_SPIKE_MIN_GB` на ноду (15 ГБ при 150 ГБ), и в выборку попадает тот, кто разложил трафик поровну по 10 нодам. При закрытии суток порог — 100 МБ на ноду: того, кто размазал 200 ГБ по 16 нодам (по 12.5 ГБ на каждой), днём не видно, но после смены суток он найдётся. На реальной панели пользователь за сутки в среднем проходит через ~5 нод.

**Нагрузка на панель.** Около 49 запросов статистики в сутки (48 дневных и один ночной) при любом числе подписок, плюс лёгкий запрос списка нод перед каждым опросом. Запросов на каждого пользователя нет. Запрос читает только строки за одни сутки по первичному ключу таблицы `nodes_user_usage_history`. Замер на панели с 25 нодами и ~2 500 активными пользователями в сутки:

- дневной запрос — 0.4 с и 34 КБ;
- ночной — 1.4 с и 420 КБ;
- первый запуск с догрузкой 14 суток — около 5 с;
- история в Redis — около 3 МБ.

На 50 000 подписок (примерно в 10 раз больше активных пользователей) стоит ожидать дневной запрос в 1–4 с, ночной в 5–15 с и около 4 МБ, историю около 30 МБ.

**Почему такие значения по умолчанию.** Они подобраны по замерам на той же панели. Медиана суточного трафика там 3.5 ГБ, у 99% пользователей — до 34 ГБ. С порогами ×5 и 30 ГБ всплеск срабатывал бы ~9 раз в сутки, с ×10 и 100 ГБ — ~1.3 раза. И это уже действительно аномалии: 185 ГБ при норме 6 ГБ, 105 ГБ при норме 2.6 ГБ. Правило «100 ГБ в 5 из 7 суток» за неделю сработало на одного пользователя с 1.1 ТБ в сутки. Число алертов растёт вместе с числом пользователей, поэтому значения по умолчанию взяты с запасом: 150 ГБ для всплеска и 200 ГБ для постоянно высокого трафика. На небольшой панели их можно снизить до 100 ГБ. Лимиты трафика тарифов панель отслеживает сама (`BANDWIDTH_USAGE_NOTIFICATIONS_THRESHOLD`).

Нужен scope `bandwidth-stats:node-usage`; без него лимитер один раз пишет предупреждение и пропускает опросы. Если в панели выключен учёт трафика пользователей (`SERVICE_DISABLE_USER_USAGE_RECORDS=true`), данных не будет, и лимитер об этом предупредит.

### Ручной режим (`ACTION_MODE=manual`)

При превышении бот отправляет алерт с кнопками:

```
⚠️ Превышение лимита устройств
┌──────────────────────┬──────────────────────┐
│ 👤 Пользователь      │ username123          │
│ 🔗 Подписка          │ открыть              │
│ 📊 Лимит             │ 3                    │
│ 📡 Обнаружено        │ 5 IP · 2 ASN         │
│ 🚦 Превышение        │ +2                   │
│ 📈 Нарушений за 24 ч │ 3                    │
│ 🕐 Время             │ сб, 29.11 04:15      │  ← в часовом поясе читателя
└──────────────────────┴──────────────────────┘
▾ 📍 IP-адреса (5)
  IP          Провайдер      Нода
  10.0.1.10   Hetzner        node-1
  10.0.3.30   Cloudflare     node-2
▸ 📥 Запросы подписки (24 за 3 ч)
▸ 📱 HWID-устройства (2)

[🔄 Сбросить подключения]
[🔒 Отключить навсегда] [🔒 Отключить на 10 мин]  ← вторая — если AUTO_DISABLE_DURATION > 0
[🔇 Игнорировать 15 мин]                           ← если IGNORE_DURATION > 0, иначе "🔇 Игнорировать"
```

**Признаки раздачи.** В основной таблице алерта две строки-сводки, а под списком IP — два свёрнутых блока с подробностями:

- «📥 Запросы подписки» — последние 24 запроса подписки из панели, сгруппированные по IP: провайдер, приложения (Happ, v2rayNG, браузер…) и сколько раз. 🟢 отмечает IP, с которого сейчас есть подключение. Сводка в таблице: `9 IP · 4 ASN · приложений: 4`.
- «📱 HWID-устройства» — устройства, которые панель зарегистрировала за пользователем: модель, система, приложение и последняя активность. Сводка в таблице: `2 / 3` (устройств / лимит).

Один телефон, который переключается между Wi-Fi и LTE, запрашивает подписку одним приложением из двух-трёх сетей. Ссылка, отданная друзьям, — это много сетей и разные приложения. Если IP больше лимита, а HWID-устройств не больше, похоже на выгруженные ключи. Данные запрашиваются только при отправке алерта (два параллельных запроса, не дольше 8 с) и требуют scope `users:subscription-request-history` и `hwid-user-devices:list-by-user`. Без них, на старой панели или с выключенной историей запросов (`SERVICE_DISABLE_SRH_RECORDS`) алерт приходит без этих блоков, а в лог один раз пишется предупреждение. Блок HWID пуст, если HWID-лимит в панели выключен.

После нажатия кнопки содержимое алерта сохраняется, кнопки исчезают, а внизу появляется итог: что сделано, кем и когда. После отключения подписки остаётся кнопка «🔓 Включить подписку» — действие можно отменить. Если алерт отредактировать нельзя (он удалён, слишком старый или Telegram отверг правку), итог приходит отдельным сообщением ответом на алерт.

Длительность «Отключить на N мин» и «Игнорировать N мин» запоминается в самой кнопке при отправке алерта: смена `AUTO_DISABLE_DURATION`/`IGNORE_DURATION` через `/settings` не меняет смысл уже отправленных кнопок. «Отключить навсегда» и «Включить подписку» снимают запланированное автовосстановление, чтобы старый таймер не включил пользователя снова.

| Кнопка | Действие |
|--------|----------|
| Сбросить подключения | Сброс активных подключений через API |
| Отключить навсегда | Перманентная деактивация подписки |
| Отключить на N мин | Временная деактивация с автовосстановлением (при `AUTO_DISABLE_DURATION > 0`) |
| Игнорировать | В whitelist: временно при `IGNORE_DURATION > 0`, иначе навсегда |

### Автоматический режим (`ACTION_MODE=auto`)

Подписка отключается автоматически, бот шлёт информационный алерт с кнопкой «Включить подписку». При `AUTO_DISABLE_DURATION > 0` подписка восстанавливается по таймеру, и в алерте видно, когда это произойдёт.

**Уведомления в пределах допуска (`AUTO_NOTIFY_SOFT=true`).** Когда нужно банить только при заметном превышении (`TOLERANCE`), но знать о тех, кто уже вышел за HWID-лимит:

| Кол-во устройств | Действие |
|------------------|----------|
| `устройств <= limit` | тишина |
| `limit < устройств <= limit+TOLERANCE` | 🔔 информационный алерт, **без бана** (с кнопками «Сбросить подключения» и «Игнорировать») |
| `устройств > limit+TOLERANCE` | 🔒 бан + алерт |

«Мягкие» предупреждения используют отдельный кулдаун (`cooldown:soft:`), **не** увеличивают счётчик нарушений за 24ч, **не** учитываются в `VIOLATION_THRESHOLD` и шлют webhook с событием `soft_violation_detected`.

## Webhook

При нарушении limiter может отправить HTTP POST на `WEBHOOK_URL` (работает в обоих режимах). К каждому запросу добавляется `X-Timestamp` (unix-время отправки). Если задан `WEBHOOK_SECRET`, добавляются заголовки:

| Заголовок | Содержимое |
|-----------|------------|
| `X-Signature-V2` | `sha256=<hex>` — HMAC-SHA256 от строки `<X-Timestamp>.<тело>`. **Рекомендуемая проверка:** подпись покрывает и время, поэтому переигранный запрос с новым `X-Timestamp` её не пройдёт. Отбрасывайте запросы, у которых `X-Timestamp` старше нескольких минут |
| `X-Signature` | `sha256=<hex>` — HMAC-SHA256 только от тела. Для совместимости: защищает от подмены, но не от повтора |
| `X-Webhook-Secret` | Сам секрет, для простой сверки. Кто увидел один запрос, узнаёт секрет и может подписать что угодно — отключите `WEBHOOK_SECRET_HEADER=false`, если получатель проверяет подпись |

Проверка на получателе (псевдокод): `hmac_sha256(secret, ts + "." + body) == header["X-Signature-V2"]` и `now − ts < 300`.

Отправка не блокирует цикл мониторинга. При сетевой ошибке, 5xx или 429 доставка повторяется (до 3 попыток); 4xx считается осознанным отказом получателя и не повторяется. Событие переживает остановку сервиса: при SIGTERM limiter дожидается отправки, а не теряет её.

**Пример payload:**

```json
{
  "event": "violation_detected",
  "action_mode": "auto",
  "user": {
    "user_id": 123,
    "username": "john",
    "email": "john@example.com",
    "telegram_id": 123456789,
    "subscription_url": "https://panel.example.com/sub/abc"
  },
  "violation": {
    "ips": [
      { "ip": "1.2.3.4", "node_name": "DE-1", "node_uuid": "node-uuid-1", "last_seen": "2025-11-29T12:00:00Z", "asn": 24940, "asn_org": "Hetzner Online GmbH" },
      { "ip": "5.6.7.8", "node_name": "US-1", "node_uuid": "node-uuid-2", "last_seen": "2025-11-29T12:01:00Z" }
    ],
    "ip_count": 5,
    "device_limit": 3,
    "tolerance": 1,
    "effective_limit": 4,
    "violation_count_24h": 3,
    "device_group_count": 5,
    "grouping_mode": "ip"
  },
  "action": { "auto_disable_duration_min": 10 },
  "timestamp": "2025-11-29T12:05:00Z"
}
```

| Поле | Описание |
|------|----------|
| `event` | `violation_detected` при бане; `soft_violation_detected` для «мягкого» предупреждения (`AUTO_NOTIFY_SOFT`) |
| `action_mode` | `manual` или `auto` |
| `user` | Данные пользователя (user_id, username, email, telegram_id, subscription_url) |
| `violation.ips` | Активные IP с нодой и временем последней активности |
| `violation.ip_count` | Количество уникальных IP |
| `violation.device_limit` / `tolerance` / `effective_limit` | Лимит, допуск и эффективный лимит (`device_limit + tolerance`) |
| `violation.violation_count_24h` | Нарушений за 24 часа |
| `violation.grouping_mode` | По чему считались устройства: `ip`, `subnet` или `asn` |
| `violation.device_group_count` | Итоговое число «устройств» в выбранном режиме — именно оно сравнивается с лимитом |
| `violation.subnet_count` / `asn_group_count` | Число подсетей / ASN-групп. Присутствуют, только если режим включён |
| `violation.ips[].asn` / `asn_org` | Номер и название провайдера. Присутствуют, только если база MaxMind загружена и ASN определился |
| `action.auto_disable_duration_min` | Длительность блокировки в минутах (0 = перманентная) |
| `timestamp` | Время обнаружения (ISO 8601) |

## FAQ

**Как узнать Telegram Chat ID?** Добавьте [@userinfobot](https://t.me/userinfobot) и отправьте `/start`. Для группы/канала — [@getidsbot](https://t.me/getidsbot).

**Что если API панели недоступен?** Сервис логирует ошибку, пропускает цикл и пробует снова через `CHECK_INTERVAL`. Запросы к API повторяются до 3 раз с exponential backoff и джиттером; при 429 и 408 повтор тоже выполняется, а заголовок `Retry-After` от панели учитывается. Цикл не считается успешным, если не удалось опросить ни одну ноду, если у панели нет ни одной активной ноды или если не удалось проверить ни одного пользователя (недоступен Redis или запрос пользователей), — `/healthz` в этом случае покажет проблему.

**Можно ли использовать Redis от Remnawave?** Можно, но не рекомендуется — проект поднимает свой Redis. Для существующего укажите `REDIS_URL`.

**Как изменить лимит пользователя?** Через поле `hwidDeviceLimit` в настройках подписки в панели Remnawave.
